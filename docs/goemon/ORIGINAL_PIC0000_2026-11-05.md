# Genuine NG5E PIC0000 graphics resource catalog (2026-11-05)

Source: original user-owned 16 MiB Goemon USA ROM, SHA-256
`1603be37427a33548857fc3d2e8867ede71121c353fb631b79b44f1d94845d80`.
Decompressed image independently matches SHA-256
`e40bee20508c2e29e651dca4e47504e40f908f0a2186e34a582784bf5a64be4c`.

No ROM, graphics payloads, texture bytes or commercial character art is
committed to the Shipwright fork.

## Important new discovery

**The character-adjacent resource file at root+1 contains many small
individually headered images, not one monolithic file.** The header magic
is ASCII `PIC0000` followed by `0x1A`. Every record begins at a 16-byte
boundary in the decompressed original.

Original character groups:

| Character slot (not yet named) | Root resource ID | PIC resource ID | PIC records |
|---|---:|---:|---:|
| 0 | 288 | 289 | **12** |
| 1 | 292 | 293 | **10** |
| 2 | 296 | 297 | **11** |
| 3 | 300 | 301 | **12** |
| **All** | | | **45** |

Each of those images has header fields encoding a format marker and
plausible dimensions: **32×64** or **64×32** in all 45 records.
Among the 45, 38 have marker 15, six marker 8, and one marker 16.
No record is yet classified as an individual texture, animation frame
or palette without original rendering-code evidence.

Across the entire genuine decompressed Goemon USA ROM:

- **31** resource files begin with PIC0000.
- They contain **1,810** separately identified PIC0000 records.
- **All 1,810** image headers and positions are **16-byte aligned**.
- **1,744** records carry header word 0; **66** have 0x4000.
- Format-byte distribution: **1,531** code 15, **165** code 4,
  **75** code 8, and **39** code 16.
- Abmessungen, header flags and individual record lengths are reported;
  the payload encoding is **not yet decoded**.

Header layout recovered empirically (relative byte offsets):

| Byte offset | Length | Observed interpretation |
|---|---:|---|
| 0x00 | 8 | `PIC0000\x1A` signature |
| 0x08 | 4 | header flags (observed 0 / 0x4000) |
| 0x0C | 1 | format marker (4 / 8 / 15 / 16) |
| 0x0D | 2 | candidate image width, unsigned BE |
| 0x0F | 2 | candidate image height, unsigned BE |
| 0x11 onward | variable | encoded payload, still unparsed |

The next occurrence of the magic at the next aligned boundary
identifies the next record. The format marker is NOT automatically
assumed to be bits-per-pixel without checking the original decoder.

## Implemented tool

`tools/goemon/re/pic0000_catalog.py`

Using the user's original owned 16 MiB ROM:

```powershell
py -3 tools\goemon\re\pic0000_catalog.py "C:\Pfad\Goemon.z64" --output "C:\Pfad\character_pic_catalog.json"

# Complete ROM catalog across all 31 resources
py -3 tools\goemon\re\pic0000_catalog.py "C:\Pfad\Goemon.z64" --all --output "C:\Pfad\all_pic_catalog.json"
```

The program transparently decompresses the genuine US ROM locally
using the existing and verified Goemon decompressor. It writes
**JSON metadata only**: exact source file ID, local image start,
allocated length, dimensions, two header flags, marker and SHA-256.
It does not export or copy image pixels. The four character root IDs
still need reliable in-game name mapping, and the PIC payload codec
needs its own decoder before any Zelda rendering is possible.

Source-free synthetic tests:
`tools/goemon/re/tests/test_pic0000_catalog.py` — validates multiple
records, 0x4000 flags, byte alignment, malformed headers and no raw
asset export.
